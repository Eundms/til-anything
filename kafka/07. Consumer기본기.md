# Consumer  
- Consumer : 카프카 토픽으로부터 레코드를 읽어와서 처리 
- Consumer Group : 같은 consumer group 에 속하는 consumer들은 토픽의 partition들을 나눠서 구독
    - 같은 consumer group내에서는 두 개 이상의 consumer가 하나의 partition을 consume할 수 없다 (순서보장, offset 관리 편의)
    - 서로 다른 consumer group은 독립적으로 토픽을 consume
    - 서로 다른 consumer group이 같은 토픽을 consume 하면 독립적으로 어느 offset까지 처리되었는지 관리 


- Group ID
  - consumer가 어느 consumer group 소속인지 지정
  - consumer group 안에서 partition 분배가 자동으로 되게 하려면 반드시 group ID를 지정해야 함
  - 이는 group 단위로 각 토픽의 파티션들의 어느 offset까지 처리되었는지를 관리하기 때문
    - 그래야 컨슈머의 합류/이탈 시 이어서 consume 할 수 있음 

- Auto Commit
  - consumer 관점에서 commit은 자신이 파티션의 어느 offset부터 이어서 consume하면 되는지를 카프카 내부 토픽에 기록하는 행위
  - 내가 속한 그룹을 담당하는 group coordinator가 있는 브로커로 commit 요청을 보냄 (이걸 자동으로 할지 수동으로 할 지 결정!)
  - group coordinator는 내부 토픽(__consumer_offsets)에 어느 offset부터 이어서 consume하면 되는지 저장 (key: [groupId, topic, partition], value: [offset,..])

- KafkaConsumer instance 생성
  - 내부적으로 ClassicKafkaConsumer 혹은 AsyncKafkaConsumer 중에 하나로 동작 (group.protocol에 의해결정)
    - ClassicKafkaConsumer 
        - 파티션 할당 : 리더 컨슈머가 파티션 할당을 개선하고, 그룹 전체가 동기화를 위해 STW후 재개하는 방식
        - 스레드 : poll() 호출 시 네트워크 통신 포함 단일 스레드로 동기적으로 처리 
        - group.protocol : CLASSIC
    - AsyncKafkaConsumer
        - 파티션 할당 : 브로커가 직접 파티션 할당을 개선하며 필요한 컨슈머, 파티션만 점진적으로 반영해 STW가 없음
        - 스레드 : API를 호출하는 스레드와 네트워크 통신 담당 스레드 분리 
        - group.protocol : CONSUMER

- subscribe()
  - 어떤 토픽들을 구독할 것인지 등록
  - consumer 내부의 subscriptionState 객체를 갱신하여 구독할 토픽들의 파티션 할당 상태, 파티션 별로 처리한 마지막 포지션 등을 관리할 준비
  - 내부적으로 브로커와 네트워크 통신을 하진 않음
  - subscribe()는 마지막 호출 기준으로 전달된 토픽들을 관리 (누적 개념 아님)

- assign()
  - 어떤 토픽의 몇 번째 파티션을 consume 할지를 직접 지정하는 것

- poll()
  - KafkaConsumer 동작 방식
  - 컨슈머 애플리케이션에게 브로커로부터 받아온 레코드들을 반환
  - 구체적인 동작은 사용하는 group.protocol 설정에 따라 다름 
    - CLASSIC : 브로커에서 레코드들을 읽어오고 오프셋을 커밋하는 등의 모든 과정들이 동기로 진행
    - CONSUMER: 브로커와의 통신 포함 대부분의 기능들이 백그라운드 스레드에서 비동기로 진행 

- close()
  - 컨슈머가 정리될 때까지 최대 30초간 기다림
