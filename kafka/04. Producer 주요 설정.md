# Producer 주요 설정
>  Producer Configs 문서 확인해서 설정하기 

## Producer 객체 생성 및 Producer 핵심 설정
- `bootstrap.servers(BOOTSTRAP_SERVERS_CONFIG)`
  - 카프카 클러스터와 연결하기 위해 브로커들의 리스트를 host:port 형태의 comma 구분자로 지정 
- 모든 브로커 이름을 다 지정해줄 필요는 없음 (하나만 연결되면 전체 브로커 목록을 받아옴)
  - 안전성 측면에서 최소 2개 이상의 브로커 이름 지정하기 
- `client.id(CLIENT_ID_CONFIG)`
  - Producer에 논리적인 이름을 부여하고 싶을 떄 사용 
  - 부여된 이름은 브로커 쪽에 기록되며, Logging&Debugging, 각종 metrics 집계 및 확인 용도, 카프카를 사용하는 Client의 Quota를 client.id 단위로 설정 가능
  - client ID와 group ID를 헷갈리면 안됨 

## Serialization
- key.serializer(KEY_SERIALIZER_CLASS_CONFIG), value.serializer(VALUE_SERIALIZER_CLASS_CONFIG)


## Partitioning
- `partitioner.class (PARTITIONER_CLASS_CONFIG, null)`
  - record가 어느 파티션에 producing되어야 하는지를 결정하는 Partitioner를 지정하는 역할 

- `partitioner.ignore.keys(PARTITIONER_IGNORE_KEYS_CONFIG, false)`
  - 이 값이 true가 되면 목적지 partition을 결정하는데 key가 사용되지 않음
  - custom partitioner를 쓰게 되면 이 설정 값은 아무런 의미가 없음 

## accumulation & compression
- `batch.size(BATCH_SIZE_CONFIG, 16KB)`
  - throughput 향상을 위해 같은 partition으로 향하는 레코드들은 배치에 모아서 처리 
  - 이때, batch size를 얼마로 할 것인가를 이 파라미터가 결정
  - 단일 레코드가 batch size보다 클 경우 그 레코드 크기 만큼의 특별한 배치를 할당
  - 배치가 다 차지 않아도 linger.ms 시간 만큼만 기다렸다가 처리됨 (batch.size is upper bound)
  - 배치는 BufferPool에서 batch.size만큼 할당받아 만들어짐 
    - 만약에 너무 큰 batch.size를 만들어 두고 배치가 계속 덜 찬다면 메모리 낭비 가능성이 있다 
    -> 작은 배치 사이즈는 throughput을 낮추고, 큰 batch size는 메모리 낭비 가능성이 커짐
  - batch size를 0으로 설정하면 batch로 동작하는 것을 비활성화(disable) 시킴
  - sticky, hashing, custom 등 partitioning 방식과 상관없이 동일하게 동작하는 내용 

- `linger.ms(LINGER_MS_CONFIG, 5ms)`
  - 배치가 다 차지 않아도 linger.ms 시간만큼만 기다렸다가 처리됨 
- kafka 4.0부터 디폴트 값이 0ms -> 5ms로 바뀜
  - 링크드인, 넷플릭스 등에서 벤치마크 결과 아주 잠깐이라도 기다려서 배치로 묶어서 보내는 것이 throughput에도 훨씬 좋아지고 latency도 0ms때와 비슷하거나 오히려 더 좋아지는 결과를 확인 

- `buffer.memory(BUFFER_MEMORY_CONFIG, 32MB)`
  - BufferPool에서 batch를 위해 할당할 수 있는 메모리 상한선
  - BufferPool 내부에 재사용 목적으로 batch들을 모아두는 deque 존재 (batch.size의 batch들만 모아둠)
  - 레코드를 accumulator로 append() 했을 때 동작 원리 : accumulator.append()
    - 이미 배치가 있고 레코드를 담을 잔여 공간이 있으면 레코드를 해당 배치에 추가 
    - 없으면 BufferPool에 allocate(size, maxTimeToBlockMS) 요청
      1. 요청한 size가 batch.size와 동일하고 deque에 batch가 있으면 그걸 할당
      2. 아니면 최대 메모리 대비 여유 공간이 있으면 만들어서 할당
      3. 아니면 최대 max.block.ms 동안 기다리며 여유 공간이 생기길 대기 (`producer.send()가 블락됨`)
      4. `max.block.ms만큼 기다려도 여유 공간이 생기지 않으면 exception 발생`

- `max.block.ms(MAX_BLOCK_MS_CONFIG, 60secs)`
  - producer.send()가 최대로 대기해야 하는 시간
    - 해당 시간이 지나도록 Producer의 BufferPool이 가득차서 레코드를 배치에 담을 자리가 나지 않으면 exception 발생
  - max.block.ms는 partitionsFor(), initTransactions(), sendOffsetsToTransaction(), commitTransaction(), abortTransaction() 처럼 다른 메서드에서도 최대 블락 시간 용도로 사용됨 

- `compression.type(COMPRESSION_TYPE_CONFIG, none)`
  - 레코드를 압축해서 카프카 클러스터에 저장하고 싶을 때 사용
  - 사용 가능한 값 
    - none
    - zstd : 압축률이 gzip과 비슷한데 압축 속도는 훨씬 빠름. 비용 절감
    - lz4 : 압축 속도 최우선, 압축률은 zstd보다 못함
    - snappy : 최근 벤치마크에서 전반적으로 속도와 압축률 모두 lz4나 zstd에 밀리는 경향
    - gzip : 과거에 압축률 가장 좋았음 
  - 압축은 배치 단위로 이루어지기 때문에 배치를 더 많이 할 수록 압축 효율이 좋아짐 
    - batch.size나 linger.ms를 더 많이 늘려줄수록 압축 효율이 더 좋아짐
