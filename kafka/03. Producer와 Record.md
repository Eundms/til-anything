# Producer와 Record
- Topic 
- Partition : 이벤트가 저장되어야 할 파티션 번호
- Key : key가 있으면 hashing하여 같은 파티션에 저장 (순서보장 주의)
- Value : 저장하련는 이벤트 내용
- Timestamp : 디폴트는 레코드 생성 시간 
- Header : 부가 메타 정보 저장 용도 (추적, 식별, 스키마 버전 ... etc)

# Record가 Kafka 브로커까지 가는 과정

## 1. 이벤트 발생 -> Producer : `producer.send(record)`
### 1) Record(Topic, Partition #, Key, Value ...)를 만듦
### 2) Record가 Serialization(직렬화)됨 : serialized key, serialized value
- kafka는 바이트 배열만 저장하고 전송 
- String, Integer처럼 기본 타입에 대한 Serializer들은 org.apache.kafka.common.serialization 패키지에서 제공 
- 사용자가 정의한 객체를 카프카에 적재하고 싶다면, 범용 라이브러리 사용 or Serializer<T>인터페이스 구현한 커스텀 seralizer 로 사용
    - Avro, JSON, Protobuf, Thrift 등
- Header는 별도의 Serializer가 필요 없음
- Consumer에서는 바이트 배열을 역직렬화 
### 3) partitioning 을 통해 레코드가 할당된 파티션이 결정됨 
- partition number를 직접 명시했다면 그걸 사용
- custom partitioner가 있다면 그걸 사용해서 partition number 결정
- key가 있고 key를 무시하라는 설정을 하지 않았다면 hasing(key) 결과를 사용
- 디폴트는 sticky partitioning으로 동작 

> 순서를 보장하고 싶다면 key 설계가 중요함

### 4) accumulation (w/ compression) : `append()`
Accumulator에 append
- Topic별 partition으로 record를 내부(deque)에 저장
- 이때, 배치 단위로 저장 (batch from BufferPool)
    - 같은 타이밍에 producing된 레코드들은 배치로 묶어서 전송하는 것이 더 효율적이기 때문 (higher throughput)
- 기존 배치에 여유가 있으면 바로 저장
- 기존 배치가 없거나 여유 공간이 부족하면 새로 배치 만들고 저장  
- 압축하도록 설정했다면 버퍼에 append될 때 압축 실행 

### 5) send requests : `drain()`
-`Sender Thread`가 백그라운드에서 비동기로 동작
- `전송 가능한 배치들`을 꺼내와서 `broker단위로 그룹핑`하여 `ProduceRequest를 만든` 후 `NetworkClient`를 통해 브로커로 전송(내부에서 브로커 단위로 deque)
  - NetworkClient의 InFlightRequests를 만들어서 (<-내부에서 브로커 단위로 deque의 의미) I/O multiplexing진행
